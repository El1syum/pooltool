# Physics latency target: 2.5 seconds

Status: **not achieved on the existing preview VPS**. This is a performance
investigation and incremental optimization, not a completed worst-case SLA.
No GPU is used by the current CPU/Numba event-based solver.

New host qualification (same date): see `PHYSICS_EPYC_SERVER_20261106.md`.
The EPYC VM passed both real two-worker heavy-shot probes (32 exact results,
max 1.032 s); its standalone basic-warmup corpus retained a 2.529 s deadline
failure. The existing preview service is unchanged; no migration was performed.

## Correctness boundary

The online worker uses a private fast simulation path for the concrete stock 2D
engine. Unsupported engines, strategies, mappings and component types retain
the public path or its dynamic identity checks. Desktop simulation is unchanged.

- Batch the original motion kernels and history timestamp conversion without
  aliasing live/historical BallState arrays.
- Reuse fixed stock-layout references and workspace buffers during one
  synchronous solve; direct detector callers retain replacement semantics.
- Maintain collision-cache minima in numeric arrays, preserving dict insertion
  order for ties and falling back for unsupported numeric values.
- Reject unreachable table targets and equal-radius ball pairs only through
  their inclusive, outward-expanded pending transition window. Every surviving
  candidate still uses the original scalar collision kernel.
- Preserve the old filter's nearly-real complex roots, with conservative
  interval bounds, a complex-root tube and an additional 1 mm **no-prune** band.
  This band is not a change to physical radii. Nonfinite/extreme/unsupported
  inputs, heterogeneous pair radii and altered root-filter contracts fall back.
- Avoid expensive diagnostic array formatting when DEBUG logging is disabled.

The broadphase is bounded engineering, not a universal floating-point quartic
backward-error proof. Exact pre-change full-result goldens and per-event history
comparisons are required. No fastmath, friction/solver tolerance, event limit,
60 Hz playback sampling or termination condition is weakened. Timeouts,
rejections and incomplete simulations do not count as fast completions.

## Reproducible measurements

`online/tests/latency_corpus.py` defines 14 explicit adversarial inputs, including
the recorded 1,675-event shot, a weak dense break, maximum power/spin/elevation,
grazing/parallel contacts, scratch/respot and after-foul placement. Ball order is
part of each input hash. The checked-in oracle was captured from the unchanged
legacy detector at commit `fc9e96eea2076d01d11ba8b95287023079ac9f5e` on Windows.
Linux uses `../tests/fixtures/latency_golden_linux_v1.json`, a separately frozen
pre-change oracle from that same source revision.
The weak dense input yields 2,373 events on Windows and 2,439 on Linux; cross-OS
floating-point differences are not hidden by loosening comparisons.

```sh
python -m online.tests.latency_stress --repeats 3 --max-seconds 2.5 \
  --goldens SAME_PLATFORM_PRECHANGE.json --report NEW-report.json
python -m online.tests.profile_worker_latency --repeats 3 --max-seconds 2.5 \
  --goldens SAME_PLATFORM_PRECHANGE.json --report NEW-workers.json
```

The first invocation of every case is included after common engine warmup.
`latency_stress` times full calculation plus full JSON. The worker probe waits for
two real `init_physics` workers and measures individual and simultaneous heavy
shots, including queue/IPC and full JSON. Golden validation is outside the clock.
Both reject existing report paths and invalid/nonfinite bounds. Neither accesses
live matches or the persistent database. These finite probes exclude network,
database work and the separate 500 ms shared playback lead; they do not establish
an arbitrary-load or all-possible-input SLA.

## Evidence so far

On the development machine (Ryzen AI 9 H 465), the final-candidate 14-case,
three-repeat full-result check passed all pre-change goldens, with maximum
calculation plus JSON **0.699 s**. The final real two-worker probe also passed
all twelve exact comparisons, maximum **0.645 s** including queue/IPC and JSON,
with simultaneous mixed heavy shots included. These are development-machine
measurements, not preview-server timings.

The preview exposes six KVM vCPUs, reported as Xeon E3-12xx v2/Ivy Bridge
(the host model may be masked). No service CPU quota was found. Paired Linux
weak-break comparisons before the last pair-pruning experiment measured median
10.078 s using the stock loop versus 8.467 s using the optimized online path
(1.19x speedup). All complete results, including 2,439 events and 240 playback
frames, were identical. Different unpaired runs fluctuate substantially; a
single best timing is not used as a guarantee.

The target remains unmet on this host. Additional cores primarily increase the
number of simultaneous matches, not the speed of one sequential event chain.
A hardware decision must be based on running this exact acceptance probe on the
candidate CPU and under the intended admitted concurrency. Do not purchase a GPU
as a drop-in fix for the current CPU solver. A strict response deadline also
requires an explicit supported-load/capacity policy; an unbounded queue cannot
meet a fixed deadline.

## Final target-host gates

The frozen candidate ran at
`/opt/pooltool-online/releases/20261106-physics-25s`, using the real server's
Python 3.12.3 environment, `NUMBA_NUM_THREADS=1` and persistent JIT cache. No
production process or database was changed by these isolated probes.

| Gate | Correct complete results | Maximum full calculation + serialization |
| --- | ---: | ---: |
| Linux reviewed corpus, 14 cases x 3 | 42/42 exact | 10.239 s — deadline FAIL |
| Linux real two-worker probe | 12/12 exact | 9.401 s — deadline FAIL |
| Development corpus, 14 cases x 3 | 42/42 exact | 0.699 s — finite gate PASS |
| Development real two-worker probe | 12/12 exact | 0.645 s — finite gate PASS |

On Linux the corpus deadline failures were recorded dense, weak dense, maximum
follow and maximum elevation. All of them completed with the original rules,
events, final state and 60 Hz frames. Both worker children were stopped normally
after the probe. The worker probe's dense individual maximum was 6.866 s and
weak individual maximum 9.401 s; simultaneous maxima were 6.564/8.903 s.

An earlier frozen-candidate corpus pass measured 10.711 s maximum. After review
added a stricter fallback for custom ball mappings, the repeated 14x3 stock-dict
corpus measured 10.239 s. This small difference is not attributed to that guard:
the stock arithmetic is unchanged and host timings fluctuate. The worker and
development probes preceded only that compatibility guard. Both failing maxima
remain evidence against the target, not a reason to select the fastest run.

## Regression and review

Final server/online/event-based/cushion suite: **486 tests and 5,373 subtests
passed** in 73.29 s (one existing Starlette/httpx deprecation warning). Focused
pruning/workspace/fixed-layout/corpus checks passed 45 tests and 33 subtests;
the final custom-mapping fallback regression also passed. Two complete dense
traces compare event type/IDs/time, every ball's rvw/motion state and every raw
historical sample, while proving actually deferred cache times are strictly
after the relevant pending transition. Independent code/spec/security review
approved the incremental code; architecture retained the documented numerical
WATCH. Neither review approved the unmet performance acceptance criterion.

Machine-readable evidence and tested-source hashes are in
`physics_latency_evidence_20261106.json`.

Extended-warmup failures now propagate before READY instead of being logged and
ignored. This ensures the covered warmup scenarios succeeded; it does not prove
that every arbitrary future Numba signature has already compiled.

**Deployment is deliberately held because the requested 2.5-second target
failed.** The active release remains `20261106-physics-latency`, PID 1024133.
The candidate is not active. Its private cache/path name is the target under
investigation, not a claim that the target was met. Client, model library,
authentication configuration and live matches were not modified. A faster-CPU
host or a larger native-engine rewrite needs a separate infrastructure/scope
decision; neither is silently purchased or substituted with a timeout.
